Second roborev round (job 46 on dbad050) found two more Medium issues in the fix itself,

### Detail of changes made:

- **`getSiteUrl()` now validates the protocol, not just parseability.** `new URL("localhost:3000")`
  does *not* throw — it parses as protocol `localhost:` with an opaque path and
  `origin === "null"`. Verified directly in node, along with the consequence: Next resolves
  relative metadata URLs via `new URL(relative, metadataBase)`, and that throws against an
  opaque-path base, so `/signatories/[id]` (whose OG image is the relative
  `/api/og/signer/<id>`) would break at metadata generation. The guard now requires
  `http:` or `https:`. Note roborev also listed `127.0.0.1:3000` and `example.com:8080` as
  behaving the same way — they don't, both throw on parse — but the `localhost:3000` case
  is real and is the likeliest typo.
- **`VERCEL_URL` is now gated on `VERCEL_ENV !== "production"`.** `VERCEL_URL` is set on
  production deployments too, and it is the per-deployment hostname
  (`…-9fk2x1.vercel.app`), not the custom domain. As written last commit, an unset or
  mis-scoped `NEXT_PUBLIC_SITE_URL` would have made the live site silently advertise a
  `*.vercel.app` origin, and `PRODUCTION_ORIGIN` would have become unreachable on the only
  host that matters.
- **New `buildPageMetadata({ title, description, ogType?, imageUrl? })`** in
  `src/lib/site-metadata.ts`. Shallow merge cuts both ways: a route that omits `openGraph`
  inherits the root's, but a route that defines one *replaces* it entirely and silently
  loses `siteName` and `type`. The hand-written blocks added last commit had exactly that
  bug, and `/signatories/[id]` has had it since it was written. `/about`,
  `/resources/[slug]`, and `/signatories/[id]` now all route through the helper, which also
  picks `summary` vs `summary_large_image` based on whether an image was supplied.
- Test count for `tests/lib/site-metadata.test.ts` went 13 → 18, including a case asserting
  that a `localhost:3000` config still yields a `metadataBase` that relative URLs resolve
  against, and one asserting `siteName`/`type` survive on child pages.
