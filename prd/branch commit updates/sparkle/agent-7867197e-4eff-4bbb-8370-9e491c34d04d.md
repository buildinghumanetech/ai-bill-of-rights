### Detail of changes made:
- **Mention rows are now written synchronously, before the action returns** (`src/server/actions/comments.ts`). They used to be inserted inside the fire-and-forget `void (async () => …)()` block, behind `listSignersForMention`, a dynamic `import("@clerk/nextjs/server")` and `clerkClient()`. `NewCommentForm` calls `router.refresh()` the instant the action resolves, so the refetch beat the insert nearly every time. Under the old prose-parsing renderer this was invisible because display did not depend on the write; making display row-driven turned it into a visible bug. Only the Clerk lookups and `sendEmail` stay deferred. A failed row write is caught and logged — the comment itself is already stored and must not fail with it.
- **A self-mention now gets a row** (same file). `others = mentions.filter(m => m.signerId !== effectiveSignerId)` ran *before* the insert, and the block returned early when `others` was empty, so picking your own name wrote nothing — the composer listed you under "Notifying" while the posted comment rendered your name plain. Rows are written for every resolved mention; the self-filter now applies only to the email fan-out. The row means "this was a mention", which is true of a self-mention; suppressing the mail is a separate delivery decision.
- **A picked short name no longer slices a longer hand-typed one** (`src/lib/comments/render-mentions.tsx`). With signers "Erik" and "Erika Anderson", picking Erik and hand-typing `@Erika Anderson` produced one range for `@Erik` inside a name nobody picked — rendering a styled `@Erik` plus a plain `a Anderson` and visually attributing that text to Erik. Longest-wins could not see it: there is no competing range when only one name has a row. Ranges whose next character is `\p{L}` or `\p{N}` are now skipped. Under-highlighting is the safe direction — the mention is still delivered, it just is not dressed up.
- **Covered the accumulate branch in the row grouping.** Neither new query test put two rows on one comment, so `if (list) list.push(...)` never executed; replacing it with an overwrite left the suite green while a two-person mention highlighted only one. New test asserts both ids, compared as a sorted set since row order is not guaranteed.
- **Fixed the `recordMentions` test helper, which had started encoding the bug.** It mirrored the old action (self-filter before insert). It now inserts every resolved mention and reports the mailed subset separately as `{ rows, mailed }`.

## Progress Update as of [2026-07-24 20:45 Pacific]
*(Most recent updates at top)*

### Summary of changes since last update
Shipped the `parseMentions` fix identified in the previous entry's audit. Rewrote the matcher to be case-insensitive, to accept first names, and to refuse to guess when a name is ambiguous. Verified in a browser harness that the old code was not merely *missing* mentions — on `@Erika` against a signer list containing both "Erika Anderson" and "Erik", it notified **Erik**, the wrong person. That reframes this from a missed-notification bug to a wrong-recipient bug.

### Detail of changes made:
- **`src/lib/comments/mentions.ts` rewritten.** Old algorithm: sort signers by display-name length desc, then require an exact, exactly-cased prefix match of the full display name after `@`. New algorithm:
  - Builds a candidate index of lowercased names: each signer's **full display name** plus their **first name** (first names only when ≥2 chars and different from the full name — single-char first names are too collision-prone).
  - Full names are layered *over* first names in the index, so a signer literally named "Dan" wins `@Dan` over another signer's first name "Dan(iel)". Test covers this.
  - A name claimed by two different signers is stored as `null` (ambiguous) and matches **nobody** rather than guessing. `@Erika` with two Erikas notifies no one; `@Erika Smith` resolves fine.
  - Requires the `@` to start a word (`i === 0 || !WORD_CHAR.test(body[i-1])`), which is what makes `bob@alice.com` stop matching signer "Alice".
  - Requires the match to *end* on a word boundary, which is what stops signer "Erik" from matching inside `@Erika`. This is the guard against the wrong-recipient bug above.
  - On an ambiguous match the cursor still advances past the consumed name (`i = end`) so we don't rescan inside it and pick up a tail fragment.
  - Exported a named `ParsedMention` interface; the return shape is unchanged, so `render-mentions.tsx` and `comments.ts` needed no signature changes.
- **`src/lib/comments/render-mentions.tsx`:** the highlight span now renders `body.slice(matchStart, matchEnd)` instead of `@{mention.displayName}`. Necessary because matching is now case-insensitive and accepts first names — echoing the canonical name would have silently rewritten the author's text (typing `@bob` would have displayed as `@Bob Smith`). `displayName` on the parse result is still the canonical name, which is what the email path wants.
- **Tests:** `tests/lib/comments.mentions.test.ts` grew from 9 to 20 tests, in two new describe blocks — `hand-typed names` (case-insensitivity, first-name matching, full-name precedence, apostrophe boundary) and `refuses to guess` (ambiguous first names, shorter-name-inside-longer, email addresses, blank display names).
