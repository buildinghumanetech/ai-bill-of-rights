### Summary of changes since last update
Shipped the `parseMentions` fix identified in the previous entry's audit. Rewrote the matcher to be case-insensitive, to accept first names, and to refuse to guess when a name is ambiguous. Verified in a browser harness that the old code was not merely *missing* mentions — on `@Erika` against a signer list containing both "Erika Anderson" and "Erik", it notified **Erik**, the wrong person. That reframes this from a missed-notification bug to a wrong-recipient bug.

### Detail of changes made:
- **`src/lib/comments/mentions.ts` rewritten.** Old algorithm: sort signers by display-name length desc, then require an exact, exactly-cased prefix match of the full display name after `@`. New algorithm:
  - Builds a candidate index of lowercased names: each signer's **full display name** plus their **first name** (first names only when ≥2 chars and different from the full name — single-char first names are too collision-prone).
  - Full names are layered *over* first names in the index, so a signer literally named "Dan" wins `@Dan` over another signer's first name "Dan(iel)". Test covers this.
  - A name claimed by two different signers is stored as `null` (ambiguous) and matches **nobody** rather than guessing. `@Erika` with two Erikas notifies no one; `@Erika Smith` resolves fine.
  - Requires the `@` to start a word (`i === 0 || !WORD_CHAR.test(body[i-1])`), which is what makes `bob@alice.com` stop matching signer "Alice".
  - Requires the match to *end* on a word boundary, which is what stops signer "Erik" from matching inside `@Erika`. This is the guard against the wrong-recipient bug above.
  - On an ambiguous match the cursor still advances past the consumed name (`i = end`) so we don't rescan inside it and pick up a tail fragment.
  - Exported a named `ParsedMention` interface; the return shape is unchanged, so `render-mentions.tsx` and `comments.ts` needed no signature changes.
- **`src/lib/comments/render-mentions.tsx`:** the highlight span now renders `body.slice(matchStart, matchEnd)` instead of `@{mention.displayName}`. Necessary because matching is now case-insensitive and accepts first names — echoing the canonical name would have silently rewritten the author's text (typing `@bob` would have displayed as `@Bob Smith`). `displayName` on the parse result is still the canonical name, which is what the email path wants.
- **Tests:** `tests/lib/comments.mentions.test.ts` grew from 9 to 20 tests, in two new describe blocks — `hand-typed names` (case-insensitivity, first-name matching, full-name precedence, apostrophe boundary) and `refuses to guess` (ambiguous first names, shorter-name-inside-longer, email addresses, blank display names). Added one test to `tests/lib/comments.render-mentions.test.tsx` asserting the span shows typed text. All 9 original tests kept and still pass unmodified.
- **Verification run:** `vitest run` on the three mention-touching files → 42/42 pass. `tsc --noEmit` → clean. `eslint` on the changed files → clean. Full suite: 194/198, with 4 failures in `tests/server/selfie.review.test.ts` and `tests/server/revoke.test.ts`; confirmed pre-existing by stashing my changes and re-running those two files alone (8/8 pass in isolation) — they are 15s-timeout flakes under full-suite parallel load with pglite, unrelated to this change.

Worth either raising `testTimeout` for the pglite-backed selfie tests or reducing suite parallelism, otherwise `pnpm test` stays red and stops being a useful gate.

## Progress Update as of [2026-07-24 20:00 Pacific]

### Summary of changes since last update
First entry on this branch. Docs only — no application code changed. Added a brainstorm document exploring how to make it easier for Erika to see and respond to comments (she asked specifically about SMS delivery + SMS replies, and then noted comments could live in the admin view as well). The brainstorm is deliberately pre-spec: it surveys options across three axes and ends with a phased recommendation, but commits to nothing.

### Detail of changes made:
- Added `docs/superpowers/brainstorms/2026-07-24-comment-triage-brainstorm.md`. New `brainstorms/` subdirectory alongside the existing `specs/` and `plans/` dirs, for pre-spec ideation.
- The doc opens with an audit of the current comment system, which turned up three findings worth acting on regardless of which direction we pick:
  1. **There is no notification at all when an ordinary comment arrives.** `submitCommentAction` (`src/server/actions/comments.ts:134`) only fires email for @mentions. Loading the site is the only way to learn a comment exists.
  2. **`parseMentions` (`src/lib/comments/mentions.ts:8`) requires an exact full-display-name match**, so `@Erika` does not match a display name of `Erika Anderson`. The one notification path that exists is likely silently missing real mentions in production today.
  3. **`/admin/comments` (`src/app/admin/comments/page.tsx`) has no reply UI** — only Hide/Unhide on a flat 100-row list. Notably the *server* side already supports admin replies (`submitCommentAction` handles `parentCommentId` and an admin "post as" `actAsSignerId`), so this is a missing-UI problem, not a missing-capability problem.
- Doc structure: three axes — Delivery (SMS/Twilio, Telegram, WhatsApp, email, web push, Slack, ambient surfaces, voice), Triage (admin-view-as-inbox, importance scoring, triage state table, AI digest, cadence/quiet hours, mobile inbox, weekly rollup), Response (reply-by-text and its threading problem, AI-drafted replies, one-tap ack, voice reply, delegation, public expectation-setting).
- Section B0 (admin view as the canonical inbox) was added in response to Erika's mid-session note. Framed as the *starting point*, not an alternative: push channels are pointers back to the admin view, so building pokes before the inbox can act on them is backwards.
- Recommended phasing in the doc: Phase 0 = admin inbox + reply box + notify-on-every-comment + mention fix (hours, no vendors); Phase 1 = inbound email replies via Resend per-comment reply addresses + `comment_triage` table + importance score; Phase 2 = Twilio SMS for `needs-you` only; Phase 3 = AI-drafted replies + synthesized digest.
- Two constraints documented that affect sequencing: **no cron/scheduled-job infrastructure exists** (no `vercel.json`), which any digest needs; and **US A2P 10DLC registration** gates Twilio SMS by days of paperwork, which is why SMS is not the fastest path to a prototype and why Telegram is called out as the fast alternative.

### Potential concerns to address:
- The `parseMentions` exact-match bug is a live production issue, not a hypothetical. Small fix, should probably be pulled out of this brainstorm and shipped on its own.
- Reply-by-SMS posts publicly under Erika's name. The doc flags the safety rails as mandatory (undo window, confirmation echo, don't treat a phone number alone as authorization since caller ID is spoofable) — if this gets specced, those cannot be deferred to "later."
- AI-drafted or AI-sent replies on a site about AI ethics must be labeled as such. Called out in the doc; worth making an explicit spec requirement rather than an implementation detail.
- No notion of read/unread/handled exists in the schema, so there is currently no way to state truthfully how many comments are outstanding. Any triage feature needs this table first.
- Notification fatigue is the failure mode that invalidates the whole effort — if Erika mutes the channel, none of it matters. This is the argument for building the ranking before the texting, and it should survive into any spec.
