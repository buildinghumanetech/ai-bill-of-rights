### Detail of changes made:
- Added `docs/superpowers/brainstorms/2026-07-24-comment-triage-brainstorm.md`. New `brainstorms/` subdirectory alongside the existing `specs/` and `plans/` dirs, for pre-spec ideation.
- The doc opens with an audit of the current comment system, which turned up three findings worth acting on regardless of which direction we pick:
  1. **There is no notification at all when an ordinary comment arrives.** `submitCommentAction` (`src/server/actions/comments.ts:134`) only fires email for @mentions. Loading the site is the only way to learn a comment exists.
  2. **`parseMentions` (`src/lib/comments/mentions.ts:8`) requires an exact full-display-name match**, so `@Erika` does not match a display name of `Erika Anderson`. The one notification path that exists is likely silently missing real mentions in production today.
  3. **`/admin/comments` (`src/app/admin/comments/page.tsx`) has no reply UI** — only Hide/Unhide on a flat 100-row list. Notably the *server* side already supports admin replies (`submitCommentAction` handles `parentCommentId` and an admin "post as" `actAsSignerId`), so this is a missing-UI problem, not a missing-capability problem.
- Doc structure: three axes — Delivery (SMS/Twilio, Telegram, WhatsApp, email, web push, Slack, ambient surfaces, voice), Triage (admin-view-as-inbox, importance scoring, triage state table, AI digest, cadence/quiet hours, mobile inbox, weekly rollup), Response (reply-by-text and its threading problem, AI-drafted replies, one-tap ack, voice reply, delegation, public expectation-setting).
- Section B0 (admin view as the canonical inbox) was added in response to Erika's mid-session note. Framed as the *starting point*, not an alternative: push channels are pointers back to the admin view, so building pokes before the inbox can act on them is backwards.
- Recommended phasing in the doc: Phase 0 = admin inbox + reply box + notify-on-every-comment + mention fix (hours, no vendors); Phase 1 = inbound email replies via Resend per-comment reply addresses + `comment_triage` table + importance score; Phase 2 = Twilio SMS for `needs-you` only; Phase 3 = AI-drafted replies + synthesized digest.
- Two constraints documented that affect sequencing: **no cron/scheduled-job infrastructure exists** (no `vercel.json`), which any digest needs; and **US A2P 10DLC registration** gates Twilio SMS by days of paperwork, which is why SMS is not the fastest path to a prototype and why Telegram is called out as the fast alternative.

### Potential concerns to address:
- The `parseMentions` exact-match bug is a live production issue, not a hypothetical. Small fix, should probably be pulled out of this brainstorm and shipped on its own.
- Reply-by-SMS posts publicly under Erika's name. The doc flags the safety rails as mandatory (undo window, confirmation echo, don't treat a phone number alone as authorization since caller ID is spoofable) — if this gets specced, those cannot be deferred to "later."
- AI-drafted or AI-sent replies on a site about AI ethics must be labeled as such. Called out in the doc; worth making an explicit spec requirement rather than an implementation detail.
- No notion of read/unread/handled exists in the schema, so there is currently no way to state truthfully how many comments are outstanding. Any triage feature needs this table first.
- Notification fatigue is the failure mode that invalidates the whole effort — if Erika mutes the channel, none of it matters. This is the argument for building the ranking before the texting, and it should survive into any spec.
