### Detail of changes made:
- **Regression fixed (roborev finding 3).** `#35` changed the short-name candidate to `name.split(" ")[0]` gated on `isNameLike()`. For `"Dr. Erika Anderson"` token 0 is `"Dr."`, which fails the gate, so the signer got **no** short-name candidate and `@Erika` resolved to nobody. This is the one to remember — the #35 fix for a cosmetic issue (`@Dr.` being a mention) silently broke the primary use case.
- **Wrong-recipient hole: hyphenated names (Medium).** `WORD_CHAR` was `/[\p{L}\p{N}_]/u`, and `-` is not in it, so with only signer `Jean Dupont`, the body `@Jean-Pierre` matched candidate `jean` and **notified Jean Dupont**. - **Astral letters.** `WORD_CHAR.test(body[end])` tested a single UTF-16 code unit, so an astral letter at the boundary was a lone surrogate and never counted as a word char. Extracted `isWordCharAt()`, which tests the full code point via `codePointAt` + `String.fromCodePoint`.

Strictly better — still rejects `bob@`, `josé@`, `田中@`, `bob.smith@`, and `sentence.@Alice`, while accepting all punctuation openers without an enumerated list.

Declined and documented as a KNOWN LIMITATION in the module docstring: an NFD-typed `@María` won't match an NFC-stored `María`. ### Summary of changes since last update
Shipped the `parseMentions` fix identified in the previous entry's audit. Rewrote the matcher to be case-insensitive, to accept first names, and to refuse to guess when a name is ambiguous. Verified in a browser harness that the old code was not merely *missing* mentions — on `@Erika` against a signer list containing both "Erika Anderson" and "Erik", it notified **Erik**, the wrong person. That reframes this from a missed-notification bug to a wrong-recipient bug.

### Detail of changes made:
- **`src/lib/comments/mentions.ts` rewritten.** Old algorithm: sort signers by display-name length desc, then require an exact, exactly-cased prefix match of the full display name after `@`. New algorithm:
  - Builds a candidate index of lowercased names: each signer's **full display name** plus their **first name** (first names only when ≥2 chars and different from the full name — single-char first names are too collision-prone).
  - Full names are layered *over* first names in the index, so a signer literally named "Dan" wins `@Dan` over another signer's first name "Dan(iel)". Test covers this.
  - A name claimed by two different signers is stored as `null` (ambiguous) and matches **nobody** rather than guessing. `@Erika` with two Erikas notifies no one; `@Erika Smith` resolves fine.
  - Requires the `@` to start a word (`i === 0 || !WORD_CHAR.test(body[i-1])`), which is what makes `bob@alice.com` stop matching signer "Alice".
  - Requires the match to *end* on a word boundary, which is what stops signer "Erik" from matching inside `@Erika`. This is the guard against the wrong-recipient bug above.
  - On an ambiguous match the cursor still advances past the consumed name (`i = end`) so we don't rescan inside it and pick up a tail fragment.
  - Exported a named `ParsedMention` interface; the return shape is unchanged, so `render-mentions.tsx` and `comments.ts` needed no signature changes.
- **`src/lib/comments/render-mentions.tsx`:** the highlight span now renders `body.slice(matchStart, matchEnd)` instead of `@{mention.displayName}`. Necessary because matching is now case-insensitive and accepts first names — echoing the canonical name would have silently rewritten the author's text (typing `@bob` would have displayed as `@Bob Smith`). `displayName` on the parse result is still the canonical name, which is what the email path wants.
