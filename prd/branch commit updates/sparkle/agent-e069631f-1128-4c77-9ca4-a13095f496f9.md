### Detail of changes made:

Now a total order: `earlier.signed_at < s.signed_at OR (equal AND earlier.id < s.id)`. Test added; **verified it fails without the fix**, returning `['Simultaneous','Simultaneous']`. Worth noting roborev's reasoning: equal timestamps aren't hypothetical here because bulk/admin-created signatures stamp a fixed time, and a backfill copying signature rows forward would produce them at scale.
- **`DISTINCT ON` needed the same tiebreaker (Low — fixed).** I'd added `signerId` to the *outer* ORDER BY but left the DISTINCT ON sort as `(signerId, signedAt DESC)`. With two same-timestamp signatures, which row survives is undefined — so the `version` rendered next to that person's name on `/signers` and `/signatories` was arbitrary and could change between page loads. Now `(signerId, signedAt DESC, id DESC)`, with a test that reads five times and asserts agreement.
- **Second index for the ticker (Low — fixed).** `0007` only added `(signer_id, signed_at DESC)`, which serves the DISTINCT ON sort and the correlated probe — but `listRecentSignersSince`'s *driving* predicate is `signed_at > cutoff` with no `signer_id` restriction, which that index cannot serve. `/api/signers/recent` is `force-dynamic` and polled roughly once a minute by every open homepage tab, making it the hottest of these shapes. Added `signatures (signed_at DESC)` to the migration, `schema.ts`, and the pglite test schema.
- **Missing ticker test case (Low — fixed).** Both existing tests put the re-signer's first signature outside the window (48h) or omitted it. The case where first signature *and* re-signature both fall inside the 60-minute window was untested — and it's what an "exclude anyone whose earliest signature predates the cutoff" implementation would get wrong. Added, including an assertion that the announcement carries the *first* signature's timestamp.
- **Raw `sql` → `lt()` (Low — fixed).** The correlation predicate was a raw template beside an `eq()`. Now uses `lt()`/`or()`, so a renamed or retyped column is a compile error rather than silently-wrong SQL.
- **Unjournaled-migration convention documented (Low — fixed).** `_journal.json` stops at idx 4 while 0005–0008 exist as loose files, so `drizzle-kit migrate` won't apply them and the only record that they must be run by hand was a commit message. ### Potential concerns to address:

- **Signatures do not carry forward, by design.** `getMySignatureStatus(VERSION)` filters signatures by exact version string. Everyone who signed v0.0.1 now reads as `not-signed` for v0.1.0 and will be shown the sign form again. This is arguably the correct semantic for a new version, but it means the public signature count for the *current* version starts at zero until people re-sign. Decide whether the homepage `<SignatureCount />` should count all versions or just the current one, and whether existing signers get a "re-affirm" flow rather than a cold sign form.

Publishing 0.1.0 is exactly the "minor revision" event that preference promised, and **no email will go out**. Either build that send or accept that the preference is currently decorative.
